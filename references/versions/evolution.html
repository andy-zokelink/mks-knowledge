02

起源：为什么需要 MKS

一切始于刘雪峰「最小知识集」理论：一个领域 80% 的价值，集中在 20% 的核心概念上。掌握这些概念，就能在短时间内建立对该领域的结构化认知。

Get 笔记积累了大量课程笔记——硅谷来信、谷歌方法论、数学通识、世界文明史……但这些笔记是线性的、碎片化的。需要一种方式，将海量笔记结构化提取，提炼出每门课程的核心概念网络。

最初只是单次对话中的一句：「帮我搭一下 XX 的最小知识集」。没想到这句话，开启了一场持续 3 个月的技能演化。

03

v1.0：从手工到模板

第一版 MKS 是一个单页 HTML，包含 9 个功能标签：

知识集总览 → 知识卡片 → 题库 → 考试 → 复习 → 思维导图 → 深度追问 → 案例分析 → 实战决策

其中最受欢迎的是翻转卡片设计：正面只显示概念名，点击翻转后，背面展示定义、类比、示例、反例——形成「先回忆、再验证」的主动学习闭环。

✦ v1.0 代表产出

硅谷来信1_v2：7 个专题，覆盖科技商业逻辑、思维方法论、投资财富、历史文明、艺术审美、教育成长、职场智慧。

谷歌方法论：系统化提取 Google 工程文化与思维工具。

但 v1.0 有一个巨大的痛点：手写 SVG 坐标。思维导图的每个节点位置都需要手动指定 (x, y) 坐标，每次调整布局都要改几十个坐标点，效率极低。

04

v2.0：批处理与自动化

这是最关键的一次跳跃——从「一次一个专题」到「一次一批课程」。

SQLite 本地数据库的引入，让我们摆脱了 Get Notes API 的速率限制。所有笔记下载到本地，随心所欲地查询和分析。

Graphviz 自动布局引擎彻底告别了手写 SVG 坐标的痛苦——只要定义节点和边，布局由算法自动完成。

Claude Code 并行调度是另一大突破：同时启动 7 个进程生成不同专题，3-5 个成功，失败的自动重跑。但这也带来了新问题。

✦ v2.0 新问题

  • • Claude Code 静默卡死——进程看着还在，实际已停滞
  • • 大 JSON 超过 1MB——模型输出截断导致数据结构损坏
  • • 僵尸进程延迟通知——任务失败了 10 分钟才被告知

GitHub Pages 部署让我们第一次实现了「手机电脑均可访问」——生成的 MKS 不再只是本地文件，而是可以通过 URL 分享的完整知识站点。

05

v2.20：品控体系的建立

这是用血的教训换来的版本。

文章摘要目录被当成 MKS 交付了。零概念提取，只有标题列表。我们必须全量重做。 —— v2.20 的起点：一次全量返工事故

这次事故让我们发现了一个重大区别：课程正文 MKS ≠ 笔记 MKS。笔记是学习者自己的理解和摘要，而课程正文是原作者的系统论述。两者的信息密度和结构完全不同——从笔记提取概念，比从原文提取更困难，因为笔记已经丢失了大量原作者的逻辑线索。

于是，品控铁律诞生了：

✦ 品控铁律：规则 + 复核 = 质量

质量闸门三道防线：

  1. Claude Code 自检——生成后自动运行校验脚本，检查结构完整性
  2. Hermes 浏览器复核——在真实浏览器中渲染，确认交互和视觉正确（grep 通过 ≠ 渲染正确）
  3. 用户验收——人工抽查关键专题，确认概念提取质量和叙事逻辑

此外，我们发现了三大共同回归的模式化问题：翻转卡片、题库、思维导图——不同专题的这三个模块经常出现同类错误。通过建立标杆驱动机制（用最优专题作为标准，对齐其他专题），我们大幅降低了同类错误的复发率。

06

v2.36：创意的系统化

Andy 曾三次强调：「禁止卡片罗列」。每个专题不能只是把概念卡片排成一排——那是最懒惰的设计。每个专题应该有自己独特的叙事结构和交互体验。

这推动了一次根本性的转变：从「套用统一模板」到「每个专题独立设计」。

✦ 创意模式库 · Creative Patterns（840 行可复用方法论）

隐喻选择矩阵 根据课程气质匹配合适的视觉隐喻——古典学术用档案馆、科学技术用控制台、文明史用星图
5 大叙事模式 时间轴叙事 / 概念地图 / 对话博弈 / 案例驱动 / 思维实验
13 种交互形式 翻转卡片、渐进式展开、拖拽排序、矩阵对比、时间轴滑动、关系图谱、决策树、闪卡测验、场景模拟、概念拼接、层级钻取、双栏对照、自由探索

更重要的是，我们建立了多作者体系：

Hub 总纲 → 系列首页 → 具体课程
（知识总纲） （作者门户） （知识专题）

这标志着 MKS Builder 从一个工具，跨越为一个平台。90+ references 文档，覆盖 A/B/D/E/F/G 全场景——从单次生成到持续维护，从个人使用到多作者协作。

07

核心设计哲学演变

每一次版本跃迁，都伴随着设计哲学的根本转向：

维度 v1.0 → v2.0 → v2.20 → v2.36
驱动模式 模板驱动→ 规则驱动→ 标杆驱动→ 愿景驱动
代码生成 Hermes 手写→ Claude Code 批量→ Hermes 规划 + Claude Code 执行
分发形态 单个 HTML→ GitHub Pages→ 独立仓库 + 多作者体系
体验目标 信息展示→ 交互体验→ 叙事体验
质量保障 人工目检→ 脚本自检→ 质量闸门→ 标杆 + 闸门 + Hermes
「规范驱动」→「标杆驱动」→「愿景驱动」：放权比规范更出质量。给设计师一个愿景 brief，而不是一份规范 check list。 —— 核心哲学转向

09

关键教训 Top 10

01
文章摘要目录 ≠ MKS
最大事故——把文章标题列表当作最小知识集交付，零概念提取，导致全量重做。教训：交付前必须确认「概念」二字是否落实。
v2.20 · 品控
02
课程正文必须串行
并行处理课程正文 = 质量断崖。并行适合独立专题，但同一课程的各专题之间存在隐含依赖关系，必须串行以保证一致性。
v2.0 · 架构
03
源数据标签不可信
航天专题 AI 编造内容——Get Notes 的 AI 摘要有时会「创造性补充」原文没有的信息。永远以原文为准，标签只是参考。
v2.20 · 数据
04
静默卡死有规律
Claude Code 静默卡死的主要根因是大 JSON 超过 1MB。解决方案：分片输出，每个 JSON 控制在 500KB 以内。
v2.0 · 工程
05
CDN 缓存迷惑调试
GitHub Pages 的 CDN 缓存导致「改完了但用户看不到」。调试时必须强制刷新（Ctrl+Shift+R）或使用无痕模式。
v2.0 · 部署
06
翻转卡片 CSS 三根因
WebKit 前缀缺失、父容器塌陷、ID 不匹配——三个根因导致的翻转卡片故障，每条都需要独立排查。
v1.0 · 前端
07
放权比规范更出质量
给设计师一个愿景 brief，而不是一份规范 check list。愿景驱动下产出的设计，比逐条对照规范做出来的更有灵魂。
v2.36 · 设计
08
禁止卡片罗列
每个专题必须使用 4-6 种不同的呈现方式。卡片罗列是最懒惰的设计——叙事体验来自形式的多样性。
v2.36 · 设计
09
delegate_task 不适合长任务
MKS 生成通常需要 5-15 分钟，而 delegate_task 的超时和状态管理不适合这种长时任务。改用直接调用 + 主动轮询。
v2.0 · 工程
10
Hermes 浏览器复核不可跳过
grep 通过 ≠ 渲染正确。文本层面的校验无法发现 CSS 布局问题、JS 交互异常、响应式断裂。浏览器复核是质量闸门的最后一道防线。
v2.20 · 品控

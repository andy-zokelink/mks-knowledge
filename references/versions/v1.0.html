MKS BUILDER v1.0

单页提取时代

从手动笔记到结构化知识集的第一次跃迁

2026年4月 — 5月初

📜 时代概览

MKS Builder 技能的起点。彼时「最小知识集」（Minimal Knowledge Set）概念刚刚成型——从一篇或多篇专栏文章中提取核心知识点， 并以结构化的 HTML 页面承载交互式学习体验。v1.0 的核心范式是 「单篇提取、单页呈现」， 所有内容聚合在一个 HTML 文件中，通过内联 CSS 和 JavaScript 实现翻转卡片、选择题、简答题等交互。

⚙️ 核心能力矩阵

🎯 场景 A — 单个 MKS 提取

从 Get Notes API 拉取指定文章集合，按 9 标签模板生成单一 HTML 知识集。输入为专栏标签（如「硅谷来信1」），输出为一个包含完整交互功能的 HTML 文件。

🏷️ 基础 9 标签模板

📋 知识集总览 🃏 知识卡片 📝 题库系统 🎓 考试模式 🔄 复习模式 🧠 思维导图 🔍 深度追问 📊 案例分析 🎯 实战决策

这 9 个标签构成了 MKS 最原始的交互骨架——知识输入（卡片）、理解验证（题库/考试）、深度加工（追问/案例/决策）、视觉梳理（思维导图）。

🔧 技术栈与架构

🖥️ 前端架构

  • 纯 HTML 单文件，无外部依赖
  • 内联 CSS 样式系统
  • 内联 JavaScript 实现全部交互
  • flip-card 翻转卡片（CSS 3D transform）
  • localStorage 持久化答题进度

📊 视觉技术

  • 概念关系图：手写 SVG 坐标
  • 思维导图：纯 CSS + HTML 嵌套列表
  • 翻转卡片：正面仅显示概念名
  • 选择题 + 简答题：独立 tab 分开展示

📡 数据获取

完全依赖 Get Notes API 实时查询专栏文章。每次生成 MKS 时需在线拉取原文内容，无本地缓存机制。这也意味着离线不可用，且对 API 稳定性有强依赖。

🏆 代表性产出

📘 硅谷来信1_v2

7 个专题 · 完整 9 标签 · 翻转卡片交互

v1.0 时代的标杆作品。7 个专题分别独立生成 MKS HTML，建立了专题拆分的初始范式。 每个专题包含完整的知识卡片、题库系统和思维导图。

📙 谷歌方法论

多专题 · 概念关系 SVG 手写

验证了 9 标签模板的通用性。手写 SVG 坐标绘制概念关系图， 为后续 Graphviz 自动化埋下了「必须改进」的种子。

🔑 关键设计特征

特征 说明
概念关系图手写 SVG 每个专题的概念关系图需手动计算节点坐标，效率低但精确
选择题 + 简答题独立 tab 两套题目系统各自独立展示，未合并为统一的题库界面
概念卡片仅正面显示概念名 翻转卡片的正面只展示概念名称，翻转后显示详细解释
localStorage 持久化 用户的答题记录和复习进度存储在浏览器本地，无服务端

⚠️ 已知局限

  • ✘ 无批量处理：每个专题需手动逐个生成，无法并行或自动化
  • ✘ 无 SQLite 本地库：所有数据依赖 API 实时查询，无本地存储与索引
  • ✘ API 强依赖：Get Notes API 不可用时，MKS 生成完全阻塞
  • ✘ SVG 手写坐标效率低：每个概念关系图需手动计算和调整节点位置
  • ✘ 翻转卡片设计不统一：不同专题的卡片样式和交互存在差异

⏳ 演化时间线

2026.4 初 · MKS 概念诞生

从硅谷来信专栏中提取核心知识点，首次提出「最小知识集」结构化理念。确立 9 标签模板作为 MKS 的标准骨架。

2026.4 中 · 硅谷来信1_v2

首个完整专题 MKS 产出，7 个专题全部上线。验证了单页 HTML 架构的可行性和 9 标签模板的通用性。

2026.4 末 · 谷歌方法论扩展

将 MKS 模板推广至谷歌方法论专栏，验证了跨专栏的适用性。暴露出 SVG 手写坐标和缺乏批量处理的核心痛点。

2026.5 初 · 迈向 v2.0

随着专栏数量增长和批量需求的迫切，单页提取模式已无法满足规模要求。MKS Builder 进入批处理流水线时代。
